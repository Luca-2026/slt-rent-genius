# Edge function rules
- Rental incentive agreements persist from server-validated inquiries into offers; unresolved Stripe attempts retain their immutable request and idempotency claim across errors, blocking new methods until provider reconciliation to prevent duplicate payable sessions.
- Staff rental payment choices use `_shared/staff-payment-decision.ts` and the same protected RPC as public choices; failed document reads block changes so issued invoices and settlements cannot be bypassed.
- Anruf-Kundenlinks use `_shared/customer-dossier-link.ts` with the persisted CRM ID and `aktion=ansehen`; the staff-only dossier opens without edits and survives login, avoiding name-based navigation.
- AB email/PDF and new invoice evidence must honor saved offer name/description overrides rather than linked catalogue labels; AB uses offerItemText without mutating the accepted snapshot, preventing customer-facing document drift.
- Sales inquiry offers use _shared/sales-offer.ts for bank-only payment, one-time line normalization and optional informational financing; block sales at creation, acceptance, reminders and public checkout, including legacy payment links, while preserving rental payment and refund behavior.

- Legacy B2B protocol HTML footers must use `unifiedFooterHtml` from `_shared/pdf-footer.ts`; their email PDFs use `drawUnifiedFooter` with the reservation location so both outputs match business documents.
- Online payments (Stripe) only via `_shared/stripe-pay.ts` (tested): amount = offer gross + deposit − recorded payments; the webhook books a payment into `inquiry.payments` only on an exact cent match, idempotently, so the order confirmation stays tied to full payment. Deposit refunds only via `offer-payment-admin` (admin and branch manager); in Stripe test mode only the test customer address receives a payment link.
- Fußzeile aller Geschäfts-PDFs (Angebot, Auftragsbestätigung, Rechnung, Rechnungskorrektur, Protokolle) nur über supabase/functions/_shared/pdf-footer.ts inkl. Standort der Auftragsabwicklung – eine Fußzeile, kein Auseinanderlaufen je Dokumentart.
- PDF company details come from `_shared/offer-company.ts` and `_shared/company.ts` so legal identities stay consistent.
- Route designated test-customer copies and acceptance notifications through `_shared/test-email-routing.ts` to avoid operational mailboxes.
- Stripe payment snapshots are immutable; invoices rehydrate provider receipts server-side to prevent draft edits. Credit refunds use _shared/credit-refund.ts through offer-payment-admin with persisted allocations, stable idempotency and webhook sync to prevent duplicate refunds.
- Online-Angebotsannahme nur über offer_acceptance_links + öffentliche Function offer-accept (/angebot/<token>): ein Link je Angebotsfassung, neue Fassung macht alte ungültig, Annahme atomar einmalig mit Name, Unterschrift und AGB-Bestätigung – damit keine doppelte oder veraltete Annahme entsteht.
- Vor-Ort-Annahme läuft über dieselbe offer_acceptance_links-Annahme (offer-accept action accept_onsite, Staff-JWT + can_edit_operations, accepted_channel='onsite') – nie ein zweiter Annahmepfad; Kunde erhält die Kopie per E-Mail.
- Fonio uses phone_calls, fonio-call-webhook and tested _shared/callPriority.ts for consistent lists/counters; fonio-live-lookup never books or uses AI. call-daily-digest runs at 20:00 Berlin with call_digest_log deduplication. Anhänger und Halteverbotsschilder-Sets sind online-only: liveLookup.ts kennzeichnet sie über onlineBookingOnly mit Website-Verweis (keine telefonische Aufnahme/Bestätigung), phoneCallAnalysis.ts wertet Verweis-Anrufe als info ohne open_points.
- Zeitgesteuerte Edge Functions (Cron) prüfen den Header x-cron-secret gegen public.internal_cron_secret (nur service_role) über _shared/cronAuth.ts – pg_cron liest den Wert zur Laufzeit, damit kein Fremdaufruf Mails oder interne Daten auslöst.
- Renty (Website-Chat) nur über supabase/functions/public-chat: Agent mit Katalogsuche (managed_products_public) und Werkzeug submit_rental_inquiry; Anfragen nur nach bestätigter Zusammenfassung, serverseitig validiert (renty-inquiry.ts, getestet), Quelle renty_chat, Mail an Standortpostfach, Testadressen @example.com gehen nur an das Testpostfach – damit keine erfundenen oder ungeprüften Anfragen im Portal landen.
- Zahlungsablauf nach Online-Annahme nur über offer-accept (Weiterleitung + Vorkasse-/Rechnungstext) und payment-reminder + _shared/payment-followup.ts (getestet): Nachfass-E-Mail 1 h nach Annahme einmalig (payment_followup_sent_at atomar), 24-h-Frist danach nur Portalmarkierung – damit niemand doppelt gemahnt oder automatisch storniert wird.
- Unaccepted offer followups share payment-reminder's existing hourly invocation; offer_link_deadline uses Berlin validity and snapshot start, decision triggers serialize acceptance/decline, and offer_followup_deliveries plus provider idempotency track dispatch. offer_followup_settings.live_enabled gates production rollout; test calls require the designated authenticated test customer and labelled test inquiry.
